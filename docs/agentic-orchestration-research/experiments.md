# Дизайн сравнений: простые, длинные и cross-project задачи

Часть исследования [README.md](README.md). Три эксперимента E1–E3. Общие правила:

- Правило решения фиксируется в docs до запуска, как для lean + JEV в раунде 4.
- Не менее 3 повторов на ячейку; доли принятых с интервалом Wilson 95 %; сравнение только внутри одного host.
- Качество не обещается. Отчёт показывает, где оно сохранилось, а где нет.
- OpenCode участвует только после починки gate (README, «Полезные улучшения»); иначе его строки помечаются
  «gate не работает» и не входят в решение.
- Harness: `scripts/bench_sdlc.py` с расширениями из [plan.md](plan.md) (шаги 1, 4, 5). Платные раунды
  запускает пользователь.

## Метрики (общие для E1–E3)

| Метрика | Как измеряется | Где уже есть |
|---|---|---|
| Качество | `accepted` (hidden tests, suite, lint, allowlist, changelog); `delivered_green`; для reviewer — число найденных дефектов с ручной разметкой true/false positive | `bench_sdlc.py:120-157`; разметка — вручную |
| Время до принятого результата | `elapsed_s` сессии; если ячейка отклонена — время второго хода «исправь: <проваленная проверка>» (не более одного); отчёт показывает «попыток до принятия» 1, 2 или «не принято» | `elapsed_s`, `turns`; второй ход нужно добавить как режим `--retry-on-reject` |
| Полная стоимость | Полные и uncached токены host + JEV + API-эквивалент в $ (`tests/bench/prices.json`) + стоимость повторного хода; стоимость за принятую задачу | `summarize()`; добавить токены повторного хода |
| Время инженера | Ручной протокол: два инженера, по ≥ 10 ячеек на режим, секундомер на чтение отчёта и решение «принять / вернуть / править самому»; плюс счётчик вмешательств (промпты, ручные правки) | Нет; протокол и таблица в этом файле |

Время инженера нельзя снять автоматически. Если ручной протокол не выполняется, отчёт пишет «не измерено»,
а не оценку.

## E1. Простые задачи

- **Вопрос.** Какой режим даёт не меньше принятых задач, чем plain, при минимальной стоимости и минимальном
  времени инженера? Нужен ли reviewer?
- **Host.** Claude, Codex; OpenCode после починки gate.
- **Режимы.** `plain`, `lean`, `lean-noreviewer`, `lean-jev` (только если JEV остаётся в целевом решении,
  вопрос 2 в README).
- **Задачи.** T1–T7 как есть; новые T8 (скрытый дефект логики с явным критерием приёмки, который lint и suite не
  ловят), T10 (вопрос, ответ на который требует правила из `.agent/rules/`), T11 (вопрос о потоке данных в
  репозитории на ~2k строк — для explorer). Графы оценки самотестируются (`make bench-selftest`).
- **Объём.** 2 host × 4 режима × 10 задач × 3 повтора = 240 ячеек. По раунду 4: Claude ≈ $0.10 на ячейку
  (≈ $12 за 120 ячеек), Codex — API-эквивалент того же порядка; реальный расход плана ChatGPT не оценивается.
- **Правило решения.** Режим становится умолчанием, если на каждом host: доля принятых не ниже plain (интервалы
  пересекаются или выше), стоимость за принятую задачу ≤ 1.3 × plain, время инженера не выше plain на выборке.
  Reviewer остаётся в умолчании, если на T8 `lean` ≥ `lean-noreviewer` + 2 ячейки из 9 при стоимости ≤ 1.3 ×.
- **Угрозы валидности.** Порядок кэша (перемешивание `--seed` уже есть); модели аккаунта Codex меняются между
  раундами; фикстура остаётся маленькой — выводы не переносятся на реальные репозитории без E1′.
- **E1′ (реальные репозитории).** Те же режимы на 2–3 AF-репозиториях с их правилами и pipeline, по 2 задачи из
  реального backlog на репозиторий, 3 повтора. Принятие = зелёный `make test`/`make lint` + решение инженера.
  Запускается после ответа на вопросы 1, 4, 6.

## E2. Длинные задачи

- **Вопрос.** Теряет ли lean качество или токены на задаче из нескольких инкрементов? Помогает ли history gate
  (шаг 5) против native compaction?
- **Host.** Claude, Codex.
- **Режимы.** `lean`, `lean-history` (шаг 5), `team-jev` (справочно, один повтор на задачу из-за стоимости).
- **Задачи.** L1: feature в три инкремента в одной сессии (модель данных → репозиторий → CLI) с миграцией и
  README; каждый инкремент — отдельный промпт с критериями; принятие проверяется после каждого инкремента и в
  конце. L2: рефакторинг четырёх модулей с сохранением поведения (hidden tests на старое поведение) в два хода.
  Фикстура расширяется до ~1.5k строк, чтобы контекст рос заметно.
- **Метрики сверх общих.** Рост cached-токенов по ходам; число повторных чтений одного файла (из трассы:
  `Read`/`cat` одного пути); события compaction (если host их отдаёт в трассу); принято инкрементов из трёх.
- **Объём.** 2 host × 2 режима × 2 задачи × 3 повтора = 24 ячейки + 4 справочных team + JEV. Ячейка длится
  3–5 минут; лимит `--seconds` поднять до 900, cap uncached до 200k.
- **Правило решения.** `lean-history` включается в умолчание, если принятых инкрементов не меньше, повторных
  чтений на третьем ходе на ≥ 20 % меньше и стоимость ≤ 1.1 × lean. Иначе остаётся native compaction.
- **Угрозы.** Три хода в одной сессии — это ещё не «длинная задача» на часы; эксперимент показывает тренд, не
  предел. Compaction host меняется между версиями CLI; версию CLI писать в `result.json`.

## E3. Cross-project задачи

- **Вопрос.** Достигает ли драйвер v0 (шаг 7) «оба репозитория зелёные» не хуже инженера с двумя ручными
  сессиями, и с меньшим числом действий инженера?
- **Host.** Сначала Claude (нет ручного доверия хукам на путь), затем Codex.
- **Фикстура.** Два репозитория: `provider` (библиотека с публичным API и версией) и `consumer` (сервис с тестами,
  которые импортируют provider по пути или по версии). `relationships.json` для пары пишется вручную в формате
  repo-scan (evidence + confidence), позже заменяется реальной парой из скана.
- **Задача.** X1: изменить контракт provider (новое обязательное поле) и адаптировать consumer; критерии —
  тесты обоих зелёные, CHANGELOG в обоих, версия provider поднята. X2: баг в provider, симптом в consumer.
- **Режимы.** M0: инженер вручную запускает две сессии lean (базовая линия; протокол фиксирует каждый промпт);
  S0: одна сессия Claude с двумя рабочими каталогами (`--add-dir`), без драйвера; D0: драйвер v0.
- **Метрики сверх общих.** Оба `make test` зелёные; тесты consumer против ветки provider (проверка
  совместимости); число действий инженера (промпты + ручные правки); суммарные токены обеих сессий; wall time.
- **Объём.** 1 host × 3 режима × 2 задачи × 3 повтора = 18 ячеек; M0 — 6 ручных прогонов двух инженеров.
- **Правило решения.** D0 идёт в разработку v1, если «оба зелёные» ≥ M0 и действий инженера меньше при
  стоимости ≤ 1.5 × суммы двух lean-сессий. S0 показывает, нужен ли драйвер вообще: если S0 ≥ D0 по всем метрикам,
  драйвер не строится.
- **Угрозы.** Фикстура пары репозиториев проще реальных зависимостей (сеть, контракты через брокер). Реальная
  пара из repo-scan нужна до решения о v1. Codex потребует доверия хукам в каждом репозитории.

## Что отчёт не будет утверждать

- Что lean сохраняет качество plain на реальных репозиториях, пока нет E1′.
- Что экономия стоит дольше одного раунда: модели аккаунтов и цены меняются; `prices.json` — вторичный источник.
- Что reviewer или workflow-контракт полезны, пока H4 и H3 не подтверждены.
- Что cross-project драйвер лучше одной сессии с двумя каталогами, пока нет E3.
