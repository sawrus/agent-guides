# Адаптивная оркестрация agentic: исследование и план (AGV2)

Дата: 2026-10-26. Исследованная версия: `main` на `a9c5848` (включает PR #78, lean + JEV).
Задание: `TZ.txt` (не в репозитории). Код не менялся, платные benchmark не запускались.

Документ разбит на четыре файла:

- этот файл: карта механизмов, источники потерь, целевая архитектура, что не строить, вопросы;
- [hosts.md](hosts.md): ограничения Claude Code, Codex и OpenCode (рекомендовано / применено / наблюдалось);
- [plan.md](plan.md): приоритизированный план небольших изменений;
- [experiments.md](experiments.md): дизайн сравнений для простых, длинных и cross-project задач.

Термины: **lean** — профиль по умолчанию (главная сессия + `explorer` + `reviewer`); **team** — v1 ролевая команда;
**JEV** — внешний сервис решений (выбор workflow, модели сабагента, permission); **gate** — Stop/PreToolUse хук
`.agent/gate/gate.py`; **ячейка** — один запуск benchmark (host × задача × режим × повтор); **принято** — все
детерминированные проверки ячейки прошли (`scripts/bench_sdlc.py:120-157`).

## Допущения

- Company rules и состав проверок заданы извне. В документе они выступают как `make test`, `make lint` и файлы
  `.agent/rules/*.md`.
- Первый сценарий: ~50 репозиториев антифрода (параллельный трек `tools/repo-scan` сканирует ~139 AF-репозиториев),
  GitLab pipeline, merge решает инженер. Граф `relationships.json` из repo-scan считается доступным входом.
- Параллельный трек профилей (`~/.config/agentic/<host>/profiles`, `agentic profile use`) даст способ хранить
  lean/team/custom профили. Здесь он только упоминается как место для настроек, которые план вводит.

## Кратко: пять главных выводов

1. **Детерминированные механизмы уже дают весь измеренный выигрыш.** Единственная разница lean против plain в
   раунде 4 — задача T5 (красный lint): 7/9 против 1/9. Из трасс: Stop-gate блокировал завершение только на Claude
   (9 из 9 ячеек T5 во всех трёх не-plain режимах); на Codex lean агент сам запустил `make lint` по инструкции
   «Definition of done»; на OpenCode gate не смог продолжить сессию, и T5 там падает в 8 из 9 не-plain ячеек.
2. **Инструкционный слой (workflows, роли, «scale the process») не показал измеримой пользы.** JEV выбрал workflow
   только для T6 (`debug-issue`, 3/3 повтора на каждом host); для feature-задач T2 и T7 с явными критериями
   приёмки ответ был `low_confidence` (15 из 21 сессий на каждом host). Польза `reviewer` не отделена от шума:
   T6 и T7 plain проходит 9/9.
3. **Потери сосредоточены в фиксированной надбавке и в делегировании.** Lean стоит 1.3–1.7 × plain по полным токенам
   (медианы: Claude 156k против 94k, Codex 127k против 81k, OpenCode 160k против 123k). Team + JEV на Codex —
   $0.301 за принятую задачу против $0.072 у lean, 2 token cap на T6; на OpenCode T6 team + JEV упёрся в 480 с.
4. **Маршрутизация моделей сейчас может удорожать, а не экономить.** На Codex lean + JEV правило
   `single_eligible_model` (`extensions/codex/hooks/jev/routing.py:205-206`) без вопроса к JEV отправило
   `reviewer` на `gpt-6-astra` (27.9k и 28.0k uncached на T6), и стоимость выросла до 1.43 × lean.
5. **Нет ни одного механизма, который отделяет «сессия завершилась» от «задача принята».** Gate после `max_blocks`
   отпускает агента и пишет `released` только в `.agentic/gate/last.json` (`gate.py:125-127`); инженер видит
   это только в отчёте агента. В раунде 4 это не сработало ни разу, но и проверено не было.

Минимальное полезное изменение: **запись о приёмке в gate** (шаг 1 в [plan.md](plan.md)). Сопутствующий bugfix:
ограничить tier helper-сабагентов моделью сессии под lean (шаг 0).

## 2. Источники потерь времени, токенов и качества

Каждый пункт: что измерено, где в коде причина, что из этого следует.

### 2.1 Фиксированная надбавка lean над plain

- Измерено (раунд 4, медиана полных токенов): Claude 156k против 94k; Codex 127k против 81k; OpenCode 160k
  против 123k. По uncached разница меньше: Claude 14.8k против 11.3k, Codex 14.7k против 12.8k. По задачам
  (Claude, полные): T1 156k/90k, T2 130k/94k, T5 239k/90k, T7 229k/300k. Стоимость за принятую задачу на Claude
  почти равна ($0.095 против $0.092): надбавка в основном кэшируется.
- Причины: always-on текст 1.5–1.9k (K1), описания skills/команд/агентов, работа по Definition of done (тесты,
  CHANGELOG) 3–5k (`results.md`, root cause 3), цикл gate на T5 (+150k полных токенов на Claude: каждый блок —
  ещё один проход по кэшированному контексту).
- Вывод: на простых задачах надбавка — это цена страховки. Её нельзя убрать инструкциями; можно только не добавлять
  новые always-on тексты. Любое новое поле контракта должно быть «по требованию», а не в `AGENTS.md`.

### 2.2 Делегирование ролям

- Измерено: Codex team + JEV — 0.62 сабагента на ячейку, 165k полных токенов, $0.301 за успех (lean $0.072),
  2 token cap на T6, 18/21 принято. OpenCode team + JEV — 0.95 сабагента, T6 медиана 480 с (таймаут), 18/21.
  Set 1 (пилот): SDLC без JEV 1/9. Claude team + JEV дёшев только из-за порядка кэша (`results.md`, раунд 4).
- Причины: каждый сабагент заново грузит базовый контекст; workflow требует 6–8 шагов с документами
  (`develop-feature.md:44-98`); Codex override требует сабагента для всего нетривиального
  (`AGENTS.override.md:30-38`).
- Вывод: делегирование оправдано только измеримым выигрышем. Сейчас его нет ни на одной задаче набора.

### 2.3 Helper-сабагенты без измеренной пользы и с дорогой моделью

- Измерено: reviewer на Codex lean T7 — 22.8k uncached + 95k cached (модель сессии); на Codex lean + JEV T6 —
  27.9k и 28.0k uncached на `gpt-6-astra` (5 × цена `terra`). Результат T6/T7 без reviewer такой же (plain 9/9).
- Причина: `routing.py:205-206` маршрутизирует без вопроса, когда в пуле одна модель; пул строится из
  `model-defaults.json`, где tiers указывают на модели, которых аккаунт не отдаёт (`extensions/codex/model-tiers.json`),
  и остаётся только frontier. Tech debt 21.
- Вывод: для helper-сабагентов под lean tier не должен быть выше модели сессии; «единственная модель» не должна
  означать автоматический frontier.

### 2.4 JEV-вопрос, который почти всегда возвращает `native`

- Измерено: на каждом host и в каждом JEV-режиме 15/21 `low_confidence`, 3/21 `native_request` (T3), 3/21 workflow
  (все — T6 → `debug-issue`). Feature-задачи T2 и T7 с критериями приёмки не прошли порог 0.9 ни разу.
  Стоимость JEV ничтожна ($0.0015 на 21 ячейку), но сессия ждёт сетевой вызов на первом промпте (таймаут
  API 8 с, хука 12 с; фактическая задержка не измерена) и получает подсказку, которую benchmark не проверяет.
- Причины: порог 0.9 (`questions.py:13-16`); критерии выбора — описания workflow и `use-when` (`questions.py:193-205`);
  `develop-feature` помечен `general: false` и «только backend service» (`develop-feature.md:23-26`), а
  `development-cycle-workflow` — общий. Для фикстуры-библиотеки оба подходят «не уверенно».
- Вывод: выбор процесса по тексту промпта — слабый сигнал. Детерминированные признаки (есть ли критерии приёмки,
  сколько модулей затронуто, есть ли слово «баг») дешевле и проверяемы. JEV остаётся опциональным.

### 2.5 Gate, который не может продолжить сессию (OpenCode)

- Измерено: T5 на OpenCode: plain 1/3, lean 1/3, lean + JEV 0/3, team + JEV 0/3; `last.json` есть только в 16/21
  ячеек lean. В трассах нет сообщений gate.
- Причина: `agentic-gate.ts:62-67` реагирует на `session.execution.succeeded` и шлёт `session.prompt`; одноразовый
  клиент уже вышел (tech debt 7).
- Вывод: это потеря качества на одном host, а не проблема оркестрации. Исправление нужно до любых сравнений
  на OpenCode.

### 2.6 Контекст на входе: правила и чтения без нужды

- Измерено (раунд 1, до исправлений): Codex T2 прочитал четыре правила и запустил native explorer на 200-строчном
  репозитории (47.8k uncached, cap). После удаления таблиц правил из spec `AGENTS.md` повтор не показал лишних
  чтений (tech debt 1–2 закрыты). K4 (T3 ≤ 1.2 × plain) по uncached всё ещё не выполнен на Codex (3.28 ×), хотя по
  полным токенам lean T3 дешевле plain на Claude и Codex (73k/89k, 32k/44k).
- Причина: чтение правил — решение модели; `paths:` ограничивает только Claude.
- Вывод: для 50 репозиториев с company rules ключевой параметр — сколько правил загружается на задачу. Это надо
  измерять в evidence (список прочитанных `.agent/rules/*` уже можно снимать через PostToolUse, как
  `WORKFLOW_RESOURCES` в `adapters.py:25`).

### 2.7 Время

- Измерено: lean добавляет к медиане ячейки 4 с (Claude), 15 с (Codex), 6 с (OpenCode). Team + JEV удваивает
  время на Codex и OpenCode. Gate-цикл на T5 Claude: 31 с против 14 с plain (но plain не принят).
- Не измерено: время инженера на чтение отчёта, проверку и повторный запуск при отказе.
- Вывод: на коротких задачах время агента не критично; критично время инженера на отказы, которых benchmark не видит.

## 3. Целевая архитектура и более простые альтернативы

Принцип: каждый новый механизм должен (а) переиспользовать существующий runtime (gate, JEV-записи, frontmatter
workflow, benchmark), (б) иметь измеряемую гипотезу и (в) быть отключаемым одним флагом. Ниже шесть гипотез из ТЗ,
для каждой — текущее состояние, простейшая альтернатива и решение.

### 3.1 Разделить выбор процесса, необходимость делегирования, выбор модели и формирование контекста

- Сейчас: четыре решения уже живут в разных местах, но два из них принимает модель по prose. Процесс: JEV-вопрос
  или slash-команда. Делегирование: модель по `AGENTS.md:17-21`. Модель сабагента: `routing.py`. Контекст:
  native-импорты + prompt сабагента, который пишет модель.
- Простейшая альтернатива: оставить делегирование по умолчанию выключенным (lean) и заменить prose на один
  детерминированный сигнал после правок: «diff затрагивает ≥ N модулей и reviewer не запускался → подсказка в
  Stop-хуке». Это ещё одна ветка в `gate.py`, не новый механизм.
- Решение: не строить классификатор задач. Сначала измерить пользу reviewer (experiments.md, E1); подсказку
  вводить только если польза измерена. Контекст сабагента стандартизировать шаблоном «пакета задачи» (п. 3.4).

### 3.2 Структурированный контракт этапов поверх Markdown workflows

- Сейчас: frontmatter даёт `inputs`, `outputs`, `roles`, `selection`, `quality-gates` (текст). Шаги — prose.
  Gate исполняет только `commands` из `.agent/gate.json`.
- Простейшая альтернатива: добавить в frontmatter workflow поле `checks:` (список команд) и `artifacts:` (пути),
  а в gate — чтение этих полей для workflow, который выбран в сессии (JEV-контекст уже хранит `workflow`,
  `hook.py:249`; команда-обёртка знает id). Без JEV workflow берётся из slash-команды: обёртка может записать
  `.agentic/task.json` одной строкой. Никакого исполнителя этапов.
- Что не нужно: DAG-движок, статусы этапов, «независимое review» как обязательный этап. Независимое review уже
  есть как `reviewer` и как code-review-workflow; его обязательность должна следовать из измерений.
- Решение: контракт v0 = `checks` + `artifacts` + существующий gate (plan.md, шаг 3). Зависимости между этапами не
  вводить, пока нет длинных задач в benchmark.

### 3.3 Выбор модели по назначению и измеренной эффективности

- Сейчас: tiers + суждение JEV по тексту назначения; на Claude и Codex цены неизвестны, `relative_cost` = null.
  Измеренной эффективности нет: ни one spawn не записывает «модель → токены → принято».
- Простейшая альтернатива: статические умолчания по назначению (explorer = fast tier, reviewer = модель сессии)
  плюс правило «под lean не выше модели сессии» (tech debt 21). Ledger собирать из уже существующих данных:
  benchmark пишет `tokens.agents` с моделью и путём агента (`bench_sdlc.py:325-328`), JEV пишет `observation`
  с `observed_model`. Обновлять `model-defaults.json` вручную по ledger раз в раунд.
- Решение: автоматическое обучение маршрутизации не строить. Сначала ledger и правило-ограничитель.

### 3.4 Ограниченный контекст и evidence с привязкой к версиям

- Сейчас: evidence разбросан: `.agentic/gate/last.json` (файлы, команды, хвосты), `.agentic/jev/event-*.json`
  (вопросы, ответы, прочитанные workflow), `.reviews/` (team). Ни один не содержит git SHA и версию pack.
- Простейшая альтернатива: расширить `last.json` полями `head` (`git rev-parse HEAD`), `pack_version`
  (из `.agentic.json`), `profile`, `accepted`, `rules_read` (из PostToolUse, по аналогии с `WORKFLOW_RESOURCES`).
  Пакет задачи для сабагента — фиксированный шаблон в `explorer.md`/`reviewer.md`: цель, критерии, изменённые
  файлы (из `git status`), команды проверок. Это правка двух Markdown-файлов и gate.
- Решение: это первый шаг плана. Память решений (MemPalace, memory-curator) не трогать: пользы не измерено,
  Codex memories уже выключены под lean из-за +1.8k токенов на запрос (`install.rs:497`).

### 3.5 Cross-project задачи

- Сейчас: ничего. Host-ограничения: Claude работает с одним проектом и дополнительными каталогами; Codex доверяет
  хукам per absolute path; gate и JEV-контекст привязаны к проекту (см. hosts.md).
- Простейшая альтернатива: внешний драйвер (как `bench_sdlc.py`), который берёт `relationships.json`, строит порядок
  репозиториев, запускает по одной host-сессии на репозиторий с общим пакетом задачи и после каждого провайдера
  запускает проверки потребителей (их `make test` против ветки провайдера). Общий граф — вход, а не новый runtime.
  Проверки совместимости — это существующие тесты потребителя, не новый вид проверок.
- Решение: не встраивать мульти-репо оркестрацию в хуки. Сначала дизайн эксперимента E3 и драйвер v0 после
  шагов 1–3.

### 3.6 Разделить завершение сессии и принятие задачи

- Сейчас: gate после трёх блоков отпускает агента (`gate.py:125-127`) и пишет `released`. Benchmark считает
  принятие внешней оценкой. В реальной работе принятие = зелёный pipeline + merge инженером.
- Простейшая альтернатива: статус `accepted: true|false` в `last.json` с причиной (`checks_failed`, `max_blocks`,
  `no_changes`), плюс `systemMessage` в выводе Stop-хука на Claude (рекомендация документации Claude Code, в коде
  не применено и не наблюдалось) и строка в финальном отчёте по инструкции. В benchmark — столбец `released`.
- Решение: шаг 1 плана. Это основа для всех последующих измерений.

### Итоговая целевая картина (после шагов 0–4)

```text
промпт → [host-native сессия, lean]
         ├─ (опц.) JEV: workflow-подсказка                 — без изменений, opt-in
         ├─ правки → PreToolUse guard                      — без изменений
         ├─ (опц.) explorer/reviewer с пакетом задачи      — шаблон в агентах, tier ≤ сессии
         └─ Stop → gate: checks (gate.json + workflow.checks)
                   → last.json {accepted, head, pack_version, checks, rules_read, released}
                   → блок / отпуск с явным «NOT ACCEPTED»
отчёт инженеру ← ссылка на last.json
cross-project (позже) ← внешний драйвер по relationships.json, по сессии на репозиторий
```

Новых постоянных процессов, баз данных и серверов нет. Новые файлы: только поля в `last.json`, поля во frontmatter
workflow и `.agentic/task.json` (одна запись на сессию).

## 4. Что пока не строить

| Не строить | Почему |
|---|---|
| Исполнитель этапов workflow (DAG, статусы, повторы) | Польза ролевого процесса не измерена; все измерения против него. `REVIEW_PIPELINE.md:4` сам фиксирует: «не runner». |
| Делегирование по решению JEV или классификатора | Делегирование в наборе задач не выигрывает; JEV для feature-задач даёт `low_confidence`. |
| Автоматический подбор моделей по истории | Нет ledger; цены Claude/Codex неизвестны; риск повторить tech debt 21. |
| Мульти-репо runtime внутри хуков | Codex trust per path, gate per project; драйвер снаружи проще и проверяем. |
| Память решений (MemPalace, memory-curator) как часть оркестрации | Пользы не измерено; Codex memories дали +1.8k токенов на запрос. |
| Новые роли или профили кроме lean/team/custom | Параллельный трек профилей покрывает хранение; новые роли увеличат контекст. |
| Расширение auto-allow permission через JEV | Отдельный риск-контур; к задаче оркестрации не относится. |
| `assisted` профиль для OpenCode (tech debt 9) | Сначала починить gate на OpenCode; иначе сравнение невалидно. |

## 5. Каких данных не хватает

1. **Длинные задачи.** Ни одна ячейка не вышла за один ход. Нужны задачи на 3+ инкремента с миграцией и
   изменением контракта (experiments.md, E2).
2. **Задачи, где plain падает не из-за lint.** T6 и T7 не разделили режимы (tech debt 17).
3. **Польза reviewer.** Нужен режим `lean` без reviewer против `lean` на задачах с скрытыми дефектами.
4. **Время инженера.** Нет ни одной метрики. Нужен протокол ручного замера на выборке (experiments.md, метрики).
5. **Реальные репозитории.** Фикстура — 200 строк Python. Нужны 2–3 AF-репозитория с настоящими правилами и
   pipeline; `make context-budget` на них.
6. **Прочитанные правила на задачу.** Нет сигнала; появится после шага 1.
7. **Цены Codex/OpenCode.** Оценки из вторичных источников; `cached_input` для OpenCode не отчитывается.
8. **Поведение Stop-хука на Codex.** В раунде 4 gate на Codex ни разу не блокировал; блокировка там не наблюдалась.
9. **Cross-project baseline.** Нет ни одного прогона: сколько ошибок совместимости делает инженер с двумя
   сессиями вручную.

## Полезные улучшения

Небольшие изменения вне основного плана; каждое можно сделать отдельной задачей.

- **Gate на OpenCode** (tech debt 7): перейти на хук, который работает до завершения хода, или документировать,
  что одноразовый `opencode run` gate не поддерживает. Без этого OpenCode-строки в сравнениях невалидны.

  Сейчас `blocks` обнуляется после успеха (`gate.py:128-131`), и факт блокировки виден только в трассе.
- **Benchmark: `verified_after_edit` для child-сессий** (tech debt 15) или удалить сигнал из отчёта.
- **`model-defaults.json` против каталога аккаунта** (tech debt 20): при install проверять, что tier-модели есть в
  `models_cache.json`, иначе не писать tier.

  workflow только для T6 (`debug-issue`). Эти факты меняют трактовку «lean + JEV = lean по качеству».
